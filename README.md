# aes-lab — шифрування файлів AES (CBC+HMAC, GCM, CTR+HMAC)

Лабораторна робота №4-5. Python 3 + бібліотека `cryptography`.

## Швидкий старт (Windows, cmd)
```
pip install -r requirements.txt
py -m unittest discover -s tests -v     :: автотести
py aes_cli.py                           :: консольний застосунок (REPL)
py tamper_demo.py                       :: імітація підміни файлу/тегу
py benchmark.py --modes cbc gcm --sizes 1MB 10MB 100MB --repeat 3
```

## Формат контейнера
```
MAGIC "AESL" (4 Б) | HDRLEN (2 Б) | JSON-заголовок | ШИФРТЕКСТ | ТЕГ GCM (16 Б) / HMAC-SHA256 (32 Б)
```
Заголовок: `v`, `mode`, `key_bits`, `key_id`, `iv`, `padding`, `orig_size`, `created`.
Заголовок автентифікується: у GCM — як AAD, у CBC/CTR — входить до HMAC (`MAGIC‖HDRLEN‖заголовок‖шифртекст`).
Для CBC/CTR працює encrypt-then-MAC: HMAC перевіряється **до** розшифрування.

## Ключі: ініціалізація та життєвий цикл
1. `key new` — запитується пароль (≥ 10 символів, літери + цифри).
2. Генерується випадковий `salt` (16 Б, `os.urandom`).
3. `PBKDF2-HMAC-SHA256` (310 000 ітерацій; нижче 200 000 — відмова) → 32-байтовий майстер-ключ.
4. HKDF розділяє його на ключ шифрування (128/192/256 біт, довжина перевіряється) і окремий ключ HMAC (256 біт).
5. У `keystore.json` пишуться лише метадані: `key_id`, `kdf`, `iterations`, `salt`, `kcv` (контрольне значення для перевірки пароля), `key_bits`, `created_at`, `expires_at`, `uses`, `max_uses`, `status`, версія формату. **Самих ключів на диску немає** — вони існують лише в пам'яті.
6. Життєвий цикл: `active` → (`revoked` за командою, вичерпання `max_uses` = 10, або через 90 днів). Шифрувати відкликаним/вичерпаним ключем заборонено (`KeyPolicyError`), розшифровувати старі файли — можна. `key rotate` створює новий ключ і відкликає старий.
7. IV/nonce щоразу випадковий (`os.urandom`), задається лише його довжина; ручне задання заборонено.

## Режими та параметри (`EncryptionParams`)
| Параметр | Значення |
|---|---|
| `mode` | `gcm` (AEAD), `cbc` (+HMAC), `ctr` (+HMAC, освітній) |
| `padding` | `pkcs7`, `ansix923` (лише CBC; CTR/GCM паддингу не потребують) |
| `iv_len` | GCM: 12 (рекомендовано) або 16; CBC/CTR: 16 |
| `block_bits` | 128 (фіксований для AES) |
| `chunk_size` | розмір шматка потокової обробки (за замовч. 1 MiB) |

Новий режим додається реалізацією гілки у `_encrypt_stream`/`_decrypt_stream` та записом у `TAG_LEN`/`DEFAULT_IV`.

## Журнал і його аналіз
Файл `logs/aes_lab.log`, один JSON на рядок: `ts`, `level`, `op` (encrypt/decrypt/key_new/...), `event` (start/finish/error), `file`, `mode`, `size`, `ms`, `tag_valid`, `error`. Секрети не логуються.

Аналіз: у застосунку `logs summary`, `logs tail 10`. Правила виявлення інцидентів:
- **ВИСОКИЙ:** `error = IntegrityError`, `tag_valid = false` — файл змінено або пошкоджено; перевірити джерело файлу й канал передачі.
- **СЕРЕДНІЙ:** ≥ 3 `BadPasswordError` для одного `key_id` — можливий підбір пароля.
- **НИЗЬКИЙ:** `KeyPolicyError` — спроба використати відкликаний/вичерпаний ключ (помилка процесу або зловмисна дія).

Як це підсилює безпеку: повторні `IntegrityError` для одного файлу → блокувати файл/джерело; серії `BadPasswordError` → ввести затримку й блокування; регулярний перегляд `uses` — планування ротації ключів.

## Ризики й рекомендації
- GCM: повтор nonce катастрофічний → випадковий 96-бітний nonce + ліміт використань ключа (10), ротація.
- CBC: без MAC піддатливий до маніпуляцій та padding oracle → лише encrypt-then-MAC; помилки не розрізняють паддинг/MAC.
- Слабкий пароль зводить нанівець PBKDF2 → мінімальні вимоги, менеджер паролів; у продуктах розглянути Argon2id/scrypt.
- Ключі в пам'яті Python не можна гарантовано затерти — для production використовувати спеціалізовані сховища (KMS/HSM).
- Організаційно: політика ротації, навчання, рев'ю коду, резервне копіювання keystore окремо від даних, моніторинг журналу.
